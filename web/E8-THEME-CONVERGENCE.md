## 3. 收敛决策与理由

**决策：以 `default` 为唯一主线主题。**

理由：
1. **功能最全**：default 是唯一覆盖了二开全部新功能的主题（运营看板、i18n、scope 等）。
2. **唯一可构建**：`air` 与 `berry` 连 `node_modules` 和锁文件都没有，
   改完**无法验证**。在没有依赖安装链路之前对它们做任何改造，等于交付未验证的代码。
3. **唯一有 i18n**：E7 已把 i18n 规范与检查脚本落在 default 上；
   另两套要各建一套词条，是纯沉没成本 —— 自研主题上线后它们的文案会被整体替换。
4. **体量相当但质量未知**：三套行数同量级，维护三套并行功能的成本是三倍，
   而收益只是"主题风格不同"。

**air / berry 的处置**：
- 保持现状（可继续作为历史参考），**不再同步新功能**；
- 在 `web/air/README.md`、`web/berry/README.md` 加冻结说明（本轮已加）；
- 若将来确需保留某套的视觉风格，做法是**把它的设计语言移植到 default**，
  而不是继续维护两套功能代码。

## 4. 自研统一主题的落地路径

自研主题不是"再写一套前端"，而是**在 default 上替换设计体系**，分四步：

1. **词条与规范先行**（已完成，E7）：`I18N-CONVENTIONS.md` + `check-i18n.js`，
   键名是契约、文案是实现 —— 换主题时词条可以整体复用。
2. **抽出展示层**：把 default 里"页面 = 数据获取 + 展示"的耦合拆开，
   展示层（表格/表单/卡片）改为可替换的组件层；数据获取层不动。
   ⚠️ 这是**最大的一块工作**，建议按页面分批（令牌 → 渠道 → 用户 → 日志 → 运营看板）。
3. **替换设计令牌**：颜色/间距/圆角/字号收敛为一组 CSS 变量或主题对象，
   新视觉只改这一层，不碰业务代码。
4. **切换构建入口**：保留 `web/default` 作为唯一构建源，
   新主题通过构建期变量或运行时主题配置切换，避免目录级分叉（那正是当前三主题困境的根因）。

## 5. 本轮（E8）实际完成的对齐

- ✅ air 主题令牌页补齐 **接口 scope（C3）** 字段 —— 这是 air 相对 default 的**唯一功能缺口**；
  同时修掉一个同类隐患：「批量新建令牌」路径原本不做 `allowed_modes` 序列化，
  会导致批量新建的令牌没有 scope、而单个编辑却有（这类不一致最难发现）。
- ✅ 量化并记录三主题差距，作为收敛决策依据。
- ❌ 未做：air/berry 的 i18n 接入与功能同步（按第 3 节决策不做）。

## 6. 风险与注意事项

1. **air/berry 的改动无法构建验证**（无 node_modules）。本轮 air 的改动仅做了
   结构与配平的静态检查（括号配平、`Select` 已导入、11 处 `allowed_modes`），
   **未经真实构建**。若要让 air 可交付，必须先补依赖安装与锁文件。
2. **不要在三主题间复制粘贴新功能**：这是当前差距的来源。新功能只进 default。
3. **自研主题的工作量**：本质是重写整个前端展示层（万行量级），
   应作为独立里程碑排期，不要与功能项混做。
